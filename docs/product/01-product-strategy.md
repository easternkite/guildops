# GuildOps 제품 전략서 (v1)

- 문서 버전: 1.0
- 작성일: 2026-02-11
- 대상: Product, Engineering, GTM
- 범위: GuildOps MVP 코드베이스(`apps/api`, `apps/web`, `packages/shared`) 기준

## 1) 문제 정의

### 1.1 현재 시장 문제
온라인 게임 길드 운영은 대부분 디스코드/스프레드시트/수동 공지/메신저로 분산되어 있어 운영 리더(길드장, 운영진)가 반복 업무에 과도한 시간을 사용한다.

| 문제 영역 | 현재 방식 | 발생 비용 | 코드베이스 연관성 |
|---|---|---|---|
| 출석 관리 | 수기 체크, 캡처 보관 | 누락/중복/분쟁 | `attendance`, `attendanceCheckIn` 모델 구현됨 |
| 멤버 관리 | 엑셀 수동 수정 | 최신성 저하 | `members` API/화면 존재 |
| 일정 운영 | 메시지 검색 기반 확인 | 일정 혼선 | `events` API 스캐폴드 존재 |
| 공지 배포 | 채널별 복붙 | 누락/반복 | `announcements` API 스캐폴드 존재 |
| 운영 증적 | “누가 무엇을 변경했는지” 추적 어려움 | 신뢰 저하 | `audit-logs` 도메인 존재(기능 확장 필요) |

### 1.2 해결해야 할 핵심 Job-to-be-Done
"길드 운영자가 매주 반복되는 출석/공지/멤버 정리/보상 정산 업무를 30분 이내로 끝내고, 운영 기록을 투명하게 남길 수 있어야 한다."

## 2) 타겟 유저

### 2.1 1차 타겟 (ICP)

| 세그먼트 | 설명 | 규모(가정) | Pain Level | 결제 의사 |
|---|---|---|---|---|
| 미드코어/하드코어 길드 운영진 | 30~200명 길드, 주 2회 이상 레이드/공대 | 높음 | 매우 높음 | 높음 |
| 멀티게임 커뮤니티 관리자 | 2개 이상 게임을 병행 운영 | 중간 | 높음 | 중간~높음 |
| 중소 e스포츠 커뮤니티 리더 | 정기 스크림/대회 운영 | 중간 | 중간 | 중간 |

### 2.2 페르소나

| 페르소나 | 목표 | 주요 불편 | 성공 기준 |
|---|---|---|---|
| 길드 마스터(Owner) | 운영 시간 단축, 이탈 감소 | 출석/보상 정합성 | 주간 운영 시간 50% 절감 |
| 운영 관리자(Admin) | 일정/공지 누락 방지 | 멤버 상태 갱신 번거로움 | 공지 실수 0건 |
| 일반 멤버(Member) | 빠른 체크인 | 절차 불명확 | 10초 내 체크인 완료 |

## 3) 핵심 가치 제안

### 3.1 Value Proposition
1. 운영의 단일 워크스페이스: 멤버/일정/공지/출석을 한 곳에서 처리.
2. 운영 신뢰성: 역할 기반 제어와 로그 중심으로 분쟁 최소화.
3. 멀티게임 최적화: 게임별 출석/운영 단위를 분리하면서 길드 단위 통합 관리.
4. 빠른 온보딩: Discord 인증 기반으로 초기 진입 장벽 최소화.

### 3.2 가치 지표

| 가치 항목 | North-star Proxy | 90일 목표 |
|---|---|---|
| 운영 시간 절감 | 주간 운영 업무 시간 | -40% |
| 운영 정확도 | 출석/보상 정정 건수 | -60% |
| 조직 신뢰 | 운영 이슈 재발률 | -30% |
| 제품 습관화 | WAU/MAU | 0.6 이상 |

## 4) 차별점

### 4.1 경쟁 대비 포지셔닝

| 항목 | 일반 커뮤니티 툴(Discord/Notion/Sheet 조합) | 범용 팀 협업 툴 | GuildOps |
|---|---|---|---|
| 길드 운영 템플릿 | 없음(직접 구성) | 제한적 | 도메인 내장형 |
| 출석-멤버-보상 연동 | 수동 | 수동 | 데이터 모델 연동 가능 |
| 역할 기반 운영 가드레일 | 약함 | 중간 | 길드 역할 중심 설계 |
| 게임 운영 특화 | 낮음 | 낮음 | 높음(멀티게임 출석/일정) |

### 4.2 현재 코드베이스 기반 강점/약점

| 구분 | 내용 | 전략적 의미 |
|---|---|---|
| 강점 | Nest + Prisma 기반 확장 가능한 백엔드 구조 | 빠른 도메인 확장 가능 |
| 강점 | 출석 및 체크인 흐름이 실제 동작 | MVP 차별 기능 검증 가능 |
| 약점 | 일부 도메인 서비스가 인메모리 CRUD | 상용 신뢰도 확보 전 보강 필요 |
| 약점 | Web UI가 관리 콘솔 초안 수준 | PMF 전후 사용자 경험 개선 필요 |
